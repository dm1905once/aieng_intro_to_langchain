Theory

LLMs are great. Unfortunately, they perform poorly when prompted to perform actions such as perform calculations, access APIs, show the weather, search the web, and others. Fortunately, LangChain allows you to combine LLMs with tools to perform various tasks. This allows you to build applications that not only understand natural language but also interact with the real world. In this stage, we'll explore the concepts of tools and how you can incorporate them into your LLM applications.

Tools

Simply put, a tool is a function that an LLM can use to perform any arbitrary processing logic. They can be anything from a simple calculator to a complex API wrapper. LangChain provides a wide variety of pre-built tools and allows you to create your own custom tools as well. You can create tools in various ways. The simplest way involves creating special functions that use the @tool decorator. We will use this method in the example below.

Imagine you want your LLM to answer questions about a specific topic by searching DuckDuckGo. You can equip it with a DuckDuckGo Search tool. LangChain offers a pre-built tool for this purpose, but let's see how we can create a simple version of such a tool from scratch:

# install the required packages:
# pip install langchain-core
from langchain_core.tools import tool

@tool("DuckDuckGoSearch")
def duckduckgoSearchTool(query: str) -> str:
    """Useful for searching the web using DuckDuckGo."""
    if "best coffee shops" in query.lower():
        return "The best coffee shops in London are: Starbucks, Costa, and Caffè Nero."
    elif "best restaurants near me" in query.lower():
        return "The best restaurants near you are:  Pizza Hut, McDonald's, and Subway."
    elif "python tutorial" in query.lower():
        return "Python tutorials can be found on platforms like Codecademy and freeCodeCamp."
    else:
        return f"No results found for your query: {query}."


# invoke the tool and pass the arguments
print(duckduckgoSearchTool.invoke({"query": "best coffee shops in London"}))

A tool needs key attributes such as a name, a description, and arguments. When using the @tool decorator these attributes can be automatically inferred. If customization is needed, you can pass the tool's name as an argument to the decorator and provide the description as a docstring. Using relevant names and a good description makes it easier for an LLM to choose the right tool. Other customization options are also available.

LangChain provides pre-built tools for common tasks, saving development time and effort. These tools can be directly imported and used, streamlining the integration process. For instance, suppose you're utilizing the DuckDuckGoSearchResults tool provided by the langchain-community library:

# install the required packages:
# pip install duckduckgo-search langchain-community
from langchain_community.tools import DuckDuckGoSearchResults

try:
    search = DuckDuckGoSearchResults()
    result = search.invoke("Best coffee shops in London")
    print(result)
except Exception as e:
    print(f"Error using DuckDuckGoSearchResults: {e}")

This example demonstrates using the DuckDuckGoSearchResults tool. The search.invoke method is used to trigger the tool, and return results from a DuckDuckGo search.

Explore LangChain's documentation on available tools. You'll find tools for searching the web, accessing databases, running shell commands, and much more. Review how you might integrate real weather APIs like OpenWeatherMap using custom tool creation.

Calling tools

Now that we understand what tools are and how to define them, let's delve into how these tools are actually used by LLMs. This process involves three key steps: binding, calling, and execution. Binding allows you to specify which tools are available for a model to use. Here, you use the .bind_tools() function. We can bind our DuckDuckGoSearch tool with a model with the following line:

# List of tools to be used with the language model
# we only have one tool but it can be more than one tool
tools_list = [duckduckgoSearchTool]

model_with_tools = llm.bind_tools(tools_list)

Based on the query, the model will determine which tools, if necessary, will be invoked and returns the tool name and the arguments to pass to the tool. We use the .invoke() function here:

user_query = "What are the best coffee shops in London?"

identified_tools = model_with_tools.invoke(user_query)

Since our query requires using a tool, the model will return the following response:

{'tool_calls': [{'id': 'call_964t', 'function': {'arguments': '{"query": "best coffee shops in London"}', 'name': 'run'}, 'type': 'function'}]}

As you can see, the model correctly identified that a tool call is needed and also selected the appropriate query (arguments) to pass to our tool. You can also view the tools that the model identified by accessing the .tool_calls attribute of the above response:

print(identified_tools.tool_calls)

The response is a JSON object with the tool's name and arguments:

[{'name': 'duckduckgoSearchTool', 'args': {'query': 'best coffee shops in London'}, 'id': 'call_qj8f', 'type': 'tool_call'}]

Finally, execute the identified tool and print the response:

response = duckduckgoSearchTool.invoke(identified_tools.tool_calls[0]) # we select the first result since we have only one tool
print(response.content)

# Output: The best coffee shops in London are: Starbucks, Costa, and Caffè Nero.

The model used our tool to determine the best coffee shops in London! If you have more than one tool, you can use a for loop.

from langchain_core.tools import tool

# Load environment variables from a .env file

    else:
        return f"No results found for your query: {query}."

tools_list = [duckduckgoSearchTool]

model_with_tools = llm.bind_tools(tools_list)

Description

Let's proceed with our question answering system. Imagine that LLMs, despite being trained on vast amounts of data, do not know the distance of planets to the Sun. Also, they cannot provide information on how long it takes planets to revolve around the Sun. However, you'd like users of your system to receive answers to such questions. Therefore, you decide to equip your system with tools that will allow your LLM to answer these questions.

In this stage, you will create three custom tools and the LLM will determine which tool to use based on the query:

  • PlanetDistanceSun — this tool should take the name of a planet as input (string) and return its approximate distance from the Sun in Astronomical Units (AU);

  • PlanetRevolutionPeriod — this tool should take the name of a planet as input (string) and return its approximate revolution period around the Sun in Earth years;

  • PlanetGeneralInfo — this tool should take the name of a planet as input (string) and handle general planet queries that are not about the planet's distance from the Sun or its revolution period. This tool should retrieve information about the planet by performing a similarity search over documents in the planets/ directory.

These tools will provide the following predefined information about planets in our solar system.

Tool 1: PlanetDistanceSun:

  • Earth — Earth is approximately 1 AU from the Sun.

  • Mars — Mars is approximately 1.5 AU from the Sun.

  • Jupiter — Jupiter is approximately 5.2 AU from the Sun.

  • Pluto — Pluto is approximately 39.5 AU from the Sun.

For any other planet name, the tool should return:

  • "Information about the distance of [planet_name] from the Sun is not available in this tool."

Tool 2: PlanetRevolutionPeriod:

  • Earth — Earth takes approximately 1 Earth year to revolve around the Sun.

  • Mars — Mars takes approximately 1.88 Earth years to revolve around the Sun.

  • Jupiter — Jupiter takes approximately 11.86 Earth years to revolve around the Sun.

  • Pluto — Pluto takes approximately 248 Earth years to revolve around the Sun.

For any other planet name, the tool should return:

  • "Information about the revolution period of [planet_name] is not available in this tool."

Tool 3: PlanetGeneralInfo:

For general queries (i.e., queries not related to distance or revolution period), this tool should perform a similarity search over documents in the planets/ directory (using embeddings) to retrieve detailed information about the specified planet. If no relevant document is found, it should return:

  • "Additional information for [planet_name] is not available in this tool."

The third tool should incorporate the logic you used in Stage three of this project.

Objectives

Here are the objectives for this stage:

  • Use the @tool() decorator to define each of these tools. Remember to provide a descriptive name for each tool as the first argument to the decorator, and a helpful docstring describing its purpose;

  • All tools should accept a single argument, planet_name of type str;

  • Inside each tool function, implement the logic to check the planet name and return the corresponding predefined information as a string, as described in the outputs for each tool. You can use if/elif/else statements or a dictionary to map planet names to their values.

  • Print the output of .tool_calls, and the output when a query is issued.
